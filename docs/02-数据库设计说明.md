# 数据库设计说明

- 数据库：`campus_secondhand`，MySQL 8.0，字符集 `utf8mb4`，排序规则 `utf8mb4_general_ci`，存储引擎 InnoDB。
- 建表脚本：`sql/01-init.sql`（自带 `CREATE DATABASE` + `USE`，可直接 `mysql < sql/01-init.sql` 执行；每张表均带字段注释与测试数据）。
- 共 **16 张表**：用户与权限 5 张、业务 7 张、记录与统计 4 张。

## 二、核心表结构

### 1. tb_user 用户表

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | bigint PK AI | 主键 |
| username | varchar(20) UK | 登录名，字母开头 4~20 位 |
| password | varchar(100) | **BCrypt 密文**，不存明文 |
| nickname | varchar(30) | 昵称 |
| avatar | varchar(255) | 头像相对路径 `/upload/avatar/...` |
| phone | varchar(20) | 手机号（可空） |
| email | varchar(80) | 邮箱，用于异步通知邮件 |
| student_no | varchar(30) | 学号 |
| campus | varchar(30) | 校区（用于同校交易筛选） |
| credit_score | int | 信用分，默认 100 |
| status | tinyint | 1 正常 / 0 禁用 |
| deleted | tinyint | 逻辑删除（MyBatis-Plus `@TableLogic`） |
| create_time / update_time | datetime | 创建/更新时间 |

索引：`uk_username`（唯一）、`idx_email`。

### 2. tb_item 闲置物品表

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | bigint PK AI | |
| seller_id | bigint | 卖家，`tb_user.id` |
| category_id | bigint | 分类，`tb_category.id` |
| title / description | varchar / text | 标题（4~60 字）、描述（10~2000 字） |
| price / original_price | decimal(10,2) | 售价 / 原价 |
| condition_level | tinyint | 成色 1~5（全新/九成新/八成新/七成新/六成新及以下） |
| cover_img | varchar(255) | 封面图 |
| campus | varchar(30) | 交易校区 |
| status | tinyint | 0 待审核 / 1 在售 / 2 已下架 / 3 已售出 / 4 审核驳回 / 5 交易中 |
| audit_remark | varchar(200) | 驳回或下架原因 |
| view_count / favorite_count | int | 浏览量（Redis 批量回写）/ 收藏数（实时维护） |
| deleted | tinyint | 逻辑删除 |
| create_time / update_time | datetime | 发布时间用于「最新发布」排序 |

索引：`idx_status_cat_price(status, category_id, price)` 覆盖列表页最常见的「在售 + 分类 + 价格区间/排序」组合；
`idx_seller(seller_id, status)` 支撑「我的闲置」；`idx_create` 支撑首页最新；`idx_title` 辅助关键词前缀检索。

### 3. tb_orders 订单表

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | bigint PK AI | |
| order_no | varchar(32) UK | 业务单号 `SC+时间戳+买家后缀+随机` |
| item_id | bigint | 物品 |
| buyer_id / seller_id | bigint | 买卖双方（冗余 seller_id 便于「我卖出的」查询，避免每次 join 物品表） |
| amount | decimal(10,2) | 成交金额（下单时快照，物品后续改价不影响历史订单） |
| status | tinyint | 0 待支付 / 1 已支付待交付 / 2 已完成 / 3 已取消（含超时关闭） |
| pay_time / finish_time | datetime | 支付/完成时间 |
| cancel_reason | varchar(100) | 取消原因（用户取消 / 超时未支付，系统自动关闭 / 管理员关闭） |
| create_time / update_time | datetime | 超时判断依据 |

索引：`uk_order_no`、`idx_buyer_status`、`idx_seller_status`、`idx_item`。
**没有** 对 `(item_id, buyer_id)` 建唯一索引——取消后同一买家需要能重新下单，重复下单由 Redis 幂等令牌 + 物品状态 CAS 控制。

### 4. tb_audit_record 审核留痕

`id / item_id / admin_id / result(1 通过、2 驳回、3 违规下架) / remark / create_time`。
每次后台审核或强制下架都会写一条，物品详情与后台审核记录页可追溯「谁在什么时候因为什么处理的」。

### 5. tb_message 站内消息

`id / user_id / title / content / biz_type(ORDER|ITEM|COMMENT|SYSTEM) / biz_id(关联业务主键) / is_read / create_time`。
消息由 RabbitMQ 消费者异步写入，前台页头红点读取未读数（`idx_user_read` 支撑）。

### 6. tb_daily_stat 每日统计

`id / stat_date(唯一) / new_user_count / new_item_count / order_count / trade_amount / cancel_count / create_time`。
由 `DailyStatTask` 每日 00:05 upsert，看板「近 7 天趋势」直接读该表，避免实时聚合大表。

### 7. tb_mail_log 邮件日志

`id / to_email / subject / biz_type(WELCOME|AUDIT|COMMENT|ORDER) / status(1 成功 0 失败) / error_msg / create_time`。
即使 `app.mail.mock=true`（答辩演示默认）也会落库，后台 `/admin/mail-logs` 可查看渲染后的主题与失败原因。

### 8. tb_payment 支付流水（担保交易）

| 字段 | 说明 |
| --- | --- |
| `pay_no` | 平台支付流水号，唯一约束 `uk_pay_no` |
| `order_id` / `order_no` | 关联订单（`UNIQUE KEY uk_order` 保证一单一流水，`idx_order` 支撑查询），金额不取页面传值，只认订单 `amount` |
| `item_id` / `item_title` | 下单时的物品快照，物品改名或删除后对账仍可读 |
| `user_id` | 付款买家（`idx_user_status` 支撑后台按人筛选） |
| `amount` | 应付金额 `DECIMAL(10,2)` |
| `channel` | `ALIPAY` / `WECHAT` / `CAMPUS_CARD`（模拟渠道） |
| `status` | 0 待支付 / 1 支付成功（托管中）/ 2 支付失败 / 3 已关闭 / 4 已结算给卖家（`idx_status` 支撑后台按状态筛选） |
| `trade_no` | 模拟网关返回的交易号 |
| `notify_time` | 网关回调时间 |
| `settle_time` | 托管款结算给卖家的时间（买家确认收货或系统自动完成时写入） |

资金语义（完整闭环）：`status=1` 表示钱已进入平台托管账户，此时物品置「已售出」；买家确认收货后订单转「已完成」，同一事务把流水 `1 → 4` 并写 `settle_time`，托管资金结算给卖家；若买家 7 天不确认收货，`OrderTimeoutTask` 每天 03:30 自动完成订单并结算，避免资金永久挂账。订单取消或超时关闭时由 `closePendingPayments` 把待支付流水置 3，不产生扣款。后台「托管中的资金」统计口径为 `tb_payment.status = 1 AND tb_orders.status = 1`（结算后流水已是 4，不会重复计入）。

## 三、设计要点

1. **规范性**：满足 3NF；订单表冗余 `seller_id`、`amount` 属于有意的读性能与快照设计（订单金额不随物品改价而变）。
2. **完整性**：登录名、订单号、收藏 `(user_id,item_id)`、角色编码、角色菜单、每日统计日期均有唯一约束；关键字段 `NOT NULL DEFAULT`。
3. **可追溯**：物品审核、违规下架留痕；邮件发送留痕；订单取消写原因；站内消息保留业务来源。
4. **逻辑删除**：`tb_user`、`tb_item` 用 `deleted` 标记，配合 MyBatis-Plus `@TableLogic` 自动过滤，避免物理删除破坏历史订单引用。
5. **性能**：为高频查询建立组合索引（见各表索引说明）；列表页分页由 MyBatis-Plus 分页插件生成 `LIMIT`；看板统计读 `tb_daily_stat` 与聚合 SQL，不扫全表。
6. **安全**：SQL 全部使用 `#{}` 预编译参数，杜绝拼接注入；密码 BCrypt；不存任何明文凭据。
7. **可重复初始化**：脚本先 `DROP TABLE IF EXISTS` 再建表，便于答辩前一键重置演示数据。

## 四、常用自检 SQL

```sql
-- 各状态物品数量
SELECT status, COUNT(*) FROM tb_item WHERE deleted = 0 GROUP BY status;

-- 订单状态分布与成交额
SELECT status, COUNT(*) cnt, SUM(amount) amount FROM tb_orders GROUP BY status;

-- 每个卖家的在售数量
SELECT u.nickname, COUNT(i.id) cnt FROM tb_user u
LEFT JOIN tb_item i ON i.seller_id = u.id AND i.status = 1 AND i.deleted = 0
GROUP BY u.id, u.nickname ORDER BY cnt DESC;

-- 最近 7 天每日统计
SELECT stat_date, new_user_count, new_item_count, order_count, trade_amount FROM tb_daily_stat
ORDER BY stat_date DESC LIMIT 7;
```
